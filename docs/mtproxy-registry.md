# Реестр MTProxy: спецификация (черновик для согласования)

Сервер сам ведёт список MTProxy, проверяет их и переключает боты на рабочий. Адреса приходят из файла
при старте и от ботов: из постов каналов, пересланных сообщений, команд администратора.
Шаг 2 (опция `--mtproxy`, один постоянный прокси) уже сделан, реестр строится поверх него.

## Термины

- **Реестр** — список прокси сервера, общий для всех его ботов.
- **Активный прокси** — тот, через который сейчас подключены все боты сервера.
- **Проверка** — запрос к Telegram через прокси (`testProxy` TDLib) с таймаутом; время ответа — пинг.

## Опции сервера

| Опция | По умолчанию | Смысл |
|---|---|---|
| `--mtproxy=<ссылка>` | | можно повторять; адреса попадают в реестр с источником `option` и не удаляются |
| `--mtproxy-file=<путь>` | | файл со ссылками: по одной в строке, `#` — комментарий; читается при старте и при изменении |
| `--mtproxy-admins=<id,id>` | | ID ботов, которым разрешены методы реестра (см. «Доступ») |
| `--mtproxy-check-interval=<сек>` | 600 | период проверки всех адресов |
| `--mtproxy-switch-timeout=<сек>` | 60 | сколько бот может быть без связи, прежде чем прокси сменится |
| `--mtproxy-expire=<часов>` | 72 | адрес, не работающий столько времени, удаляется (кроме `option` и `file`) |
| `--mtproxy-max=<n>` | 200 | предел размера реестра; при переполнении удаляются самые давно не работавшие |
| `--mtproxy-direct` | выключено | считать прямое подключение кандидатом (без прокси), предпочтительным, если работает |

Переменные окружения: `TELEGRAM_MTPROXY` (как сейчас), `TELEGRAM_MTPROXY_FILE`, `TELEGRAM_MTPROXY_ADMINS`.

## Хранение

Файл `<dir>/mtproxy.json`, запись атомарная (временный файл и переименование), переживает перезапуск:

```json
{
  "active_id": 7,
  "next_id": 12,
  "admin_token_hashes": {"123456": "sha256 токена"},
  "proxies": [
    {
      "id": 7,
      "server": "proxy.example.com",
      "port": 443,
      "secret": "ee...",
      "sources": ["option", "file", "channel:-1001234567890/45", "bot:123456"],
      "added_date": 1759750000,
      "last_check_date": 1759753600,
      "last_success_date": 1759753600,
      "last_error": "",
      "failures_in_row": 0,
      "ping": 0.231
    }
  ]
}
```

Дубли определяются по `server` (без учёта регистра), `port` и секрету в нормализованном виде
(одинаковый секрет в hex и base64url — один адрес). Повторное добавление дописывает источник.

## Методы

Методы в стиле Bot API: `POST /bot<token>/<method>`, параметры в JSON или form, ответ `{"ok": true, "result": ...}`.
Боты вызывают их через `Call` библиотек laser_tele. Методы обрабатываются самим сервером и работают,
даже когда связи с Telegram нет.

### addMTProxies

| Параметр | Тип | |
|---|---|---|
| `links` | массив строк | ссылки или произвольный текст: сервер найдёт в нём все `tg://proxy?...` и `https://t.me/proxy?...` |
| `source` | строка, необязательно | откуда адреса, например `channel:-1001234567890/45`; по умолчанию `bot:<id>` |

Результат: `{"added": 3, "known": 1, "errors": [{"link": "...", "error": "wrong secret of the MTProxy"}]}`.
Новые адреса проверяются сразу, не дожидаясь периода.

### getMTProxies

Результат: `{"active_id": 7, "direct": false, "proxies": [MTProxyInfo, ...]}`, где `MTProxyInfo` — запись реестра
с дополнительными полями:

- `link` — ссылка `tg://proxy?...`, чтобы ею можно было поделиться;
- `secret_type` — `simple`, `dd` или `ee`;
- `domain` — домен, под который маскируется `ee`-прокси;
- `state` — `unchecked`, `working` или `failing`;
- `is_active`.

### setMTProxy

`id` (число; `0` — прямое подключение). Сразу переключает боты на этот адрес. Автоматическое переключение
продолжает работать: если адрес перестанет работать, сервер сменит его.

### removeMTProxy

`id`. Удаляет адрес; если он активный, сервер переключается на лучший из оставшихся.

### checkMTProxies

Без параметров. Запускает проверку всех адресов сейчас, возвращает `true`; результаты — в `getMTProxies`.

## Доступ

Методы меняют подключение всех ботов сервера, поэтому доступны только ботам из `--mtproxy-admins`.
Одного ID в токене мало: токен вида `<id>:<что угодно>` подделывается. Поэтому сервер запоминает SHA-256
токена, с которым бот из списка хотя бы раз успешно авторизовался в Telegram, и дальше сравнивает с ним.
Сравнение локальное, доступ есть и без связи с Telegram. Первый раз связь нужна: её дают `--mtproxy` или `--mtproxy-file`.
Без `--mtproxy-admins` методы отвечают `403 Forbidden`.

## Проверка

- Проверки выполняет служебный клиент TDLib без авторизации (отдельная папка `<dir>/mtproxy-checker`):
  `testProxy` разрешён до авторизации и не мешает ботам.
- Раз в `--mtproxy-check-interval` проверяются все адреса, до 8 одновременно, таймаут 10 секунд,
  запрос к дата-центру 2. Пинг — время успешной проверки, сглаженное по последним проверкам.
- Состояния: `unchecked` (ещё не проверялся), `working` (последняя проверка успешна), `failing`.
- Адрес, не работающий дольше `--mtproxy-expire`, удаляется, кроме источников `option` и `file`.
- Прямое подключение (при `--mtproxy-direct`) проверяется `testNetwork` того же служебного клиента.

## Переключение

Признаки того, что активный прокси не работает:

- хотя бы один авторизованный бот не на связи (`updateConnectionState` не `Ready`) дольше `--mtproxy-switch-timeout`;
- две проверки активного прокси подряд неудачны.

Выбор нового адреса:

1. Кандидаты — адреса в состоянии `working`, кроме тех, что были активными и отказали за последние 10 минут.
2. Порядок: прямое подключение (если включено и работает), затем по пингу.
3. Кандидат проверяется ещё раз прямо перед переключением; если не прошёл — следующий.
4. Если рабочих нет — внеочередная проверка всех адресов; если и после неё нет — перебор по кругу
   раз в `--mtproxy-switch-timeout` (сеть могла пропасть целиком).

Пока активный прокси работает, сервер не переключается, даже если есть адрес с меньшим пингом: смена соединения
стоит дороже выигрыша.

Применение: каждому клиенту TDLib — `addProxy` с `enable=true` (TDLib сам отключает прежний) и `removeProxy`
прежнего, чтобы база бота не копила адреса. При переключении TDLib переподключается и сам догружает пропущенные
обновления; очередь `getUpdates` сервера не теряется. Каждое переключение пишется в лог сервера с причиной.

## Статистика

Страница статистики (`--http-stat-port`) показывает активный прокси и число адресов по состояниям,
без секретов.

## Бот-сборщик (laser_tele)

Пример `examples/mtproxy_collector` в laser_tele, позже то же в Rust:

- посты (`channel_post`, `edited_channel_post`) из каналов списка, где бот администратор;
- сообщения от администраторов, в том числе пересланные из любых каналов;
- ссылки берутся из текста и подписи, из `entities` (`url`, `text_link`) и из URL-кнопок —
  в каналах прокси часто публикуют под кнопками «Подключиться»;
- найденное уходит на сервер: `Call("addMTProxies", {"links": [...], "source": "channel:<id>/<message_id>"})`;
- команды администратора: `/proxies` (реестр с состояниями), `/check`, `/use <id>`, `/remove <id>`.
